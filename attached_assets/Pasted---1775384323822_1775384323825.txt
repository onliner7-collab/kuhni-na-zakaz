# Техническое задание

## Проект: сайт по продаже кухонь на заказ

### География запуска: Минск и Минская область

### География масштабирования: Москва и Санкт-Петербург

### Формат разработки: Replit + GitHub + деплой на сервер

---

# 1. Цель проекта

Создать коммерческий SEO-ориентированный сайт по продаже кухонь на заказ, который:

* генерирует заявки с органического трафика, карт и прямых заходов;
* хорошо выглядит и работает на мобильных и десктопных устройствах;
* имеет сильную конверсионную структуру;
* изначально подготовлен под продвижение в Google и Яндекс;
* может масштабироваться на новые города без полной переделки архитектуры;
* легко поддерживается через Replit и GitHub.

Основной приоритет первого этапа:

* Минск
* Минская область

Второй этап:

* Москва
* Санкт-Петербург

---

# 2. Общая бизнес-логика сайта

Сайт должен не просто показывать красивые кухни, а отвечать на три главных вопроса клиента:

1. Сколько это стоит?
2. Подойдет ли это под мою планировку и бюджет?
3. Можно ли вам доверять?

Из этого следует, что на сайте обязательно должны быть:

* каталог решений;
* страницы услуг;
* страницы по стилям / материалам / формам;
* кейсы с реальными цифрами;
* калькулятор / квиз;
* понятные цены или хотя бы диапазоны;
* отзывы;
* этапы работы;
* блок гарантий и сроков;
* контакты и локальная привязка;
* отдельные SEO-страницы под города.

---

# 3. Позиционирование и УТП

Сайт должен выглядеть как современный премиально-надежный сервис, но без излишней пафосности.

Тональность:

* уверенная;
* понятная;
* практичная;
* без перегруза техническими терминами;
* с упором на прозрачность, реальность и удобство.

Ключевые смысловые акценты:

* кухни под реальные размеры и задачи;
* прозрачный расчет стоимости;
* проектирование под бюджет;
* реальные материалы и фурнитура;
* соблюдение сроков;
* монтаж под ключ;
* реальные фото проектов;
* локальная работа по городу и области.

# 4. Целевая аудитория

## Основные сегменты

1. Владельцы квартир в Минске и области, которым нужна кухня под заказ.
2. Владельцы новостроек.

4. Клиенты, ищущие классический стиль.
5. Клиенты, выбирающие между бюджетом, средним сегментом и премиумом.

# 5. Технический стек и требования к разработке

## Базовый стек

Рекомендуемый вариант:

* Frontend: Next.js
* Styling: Tailwind CSS
* CMS/данные: локальные JSON/Markdown на старте либо headless CMS позднее
* Формы: отправка в Telegram/email/CRM webhook
* Analytics: GA4, Google Search Console, Яндекс Метрика, Яндекс Вебмастер
* SEO: SSR/SSG, metadata, sitemap, robots, schema markup

Если в Replit удобнее реализовать проще:

* React + Next.js обязательно предпочтительнее обычного SPA
* нельзя делать сайт только как клиентское SPA без нормального серверного рендера индексационных страниц

## GitHub

* проект хранится в GitHub;
* ветка main для production;
* отдельная dev-ветка для доработок;
* README с инструкцией по запуску и деплою;
* .env.example с перечнем переменных окружения;
* чистая структура папок.

## Сервер

Сайт должен быть готов к деплою на VPS/VDS.
Требования:

* HTTPS;
* nginx/reverse proxy;
* gzip/brotli;
* кэширование статики;
* корректные 301 redirect;
* защита формы от спама;
* генерация sitemap;
* корректный robots.txt.

# 17. SEO-требования

## 17.1 Общие требования

Сайт должен быть полностью подготовлен к SEO с первого дня.

### Обязательно:

* человеко-понятные URL;
* уникальные Title/Description/H1;
* корректная иерархия заголовков;
* внутренняя перелинковка;
* sitemap.xml;
* robots.txt;
* canonical;
* Open Graph;
* favicon;
* 404 страница;
* 301 редиректы;
* noindex/nofollow для технических страниц при необходимости.

## 17.2 Мета-данные

Для каждой страницы:

* уникальный title
* уникальный meta description
* уникальный H1
* SEO-friendly slug

## 17.3 Schema markup

Нужно реализовать JSON-LD для:

* Organization
* LocalBusiness
* BreadcrumbList
* FAQPage
* Review / AggregateRating при наличии корректных данных
* Product / Offer там, где это действительно уместно

## 17.4 Контентные правила

* нельзя делать пустые SEO-страницы;
* нельзя делать клонированные страницы под города;
* нельзя публиковать слабый ИИ-контент без редактуры;
* каждая важная страница должна реально отвечать на запрос пользователя.

## 17.5 Индексация

Подключить:

* Google Search Console
* Яндекс Вебмастер
* отправку sitemap
* мониторинг индексации

## 17.6 Локальное SEO

Обязательно:

* Google Business Profile
* Яндекс Бизнес
* единые NAP-данные
* реальные контакты
* категория бизнеса
* фото
* часы работы
* отзывы

## 17.7 Техническое SEO

* SSR/SSG для индексационных страниц
* быстрый TTFB
* оптимизация изображений
* lazy load
* адаптивность
* минимизация CLS
* хороший INP / LCP

## Десктопная версия

# 21. Админ-панель и система управления контентом

## 21.1 Общая задача админ-панели

На сайте должна быть полноценная защищенная административная панель, через которую можно без участия разработчика:

* менять тексты на страницах;
* менять цены и диапазоны цен;
* загружать, заменять и удалять фотографии;
* создавать, редактировать и удалять карточки кухонь;
* создавать, редактировать и удалять кейсы;
* модерировать отзывы;
* управлять локальными страницами;
* редактировать контактные данные;
* управлять FAQ;
* управлять статьями блога;
* включать и отключать отображение отдельных блоков.

Админ-панель должна быть простой, быстрой и понятной, чтобы ей мог пользоваться не только разработчик, но и владелец бизнеса или менеджер.

## 21.2 Технический формат админ-панели

Рекомендуемая реализация:

* защищенная админ-зона по URL типа /admin;
* авторизация только для допущенных пользователей;
* ролевой доступ;
* журнал действий;
* серверная валидация;
* защита от несанкционированного доступа;
* все изменения должны сохраняться в базе данных или CMS, а не в коде вручную.

Предпочтительный стек для MVP:

* Next.js admin area
* база данных: PostgreSQL / Supabase / Prisma
* хранение изображений: Supabase Storage / S3-совместимое хранилище / Cloudinary
* аутентификация: безопасная email/password или magic link система

Недопустимо:

* хранить пароли в открытом виде;
* делать гостевой доступ без ограничения времени;
* позволять любому гостю менять все разделы сайта без логирования.

## 21.3 Роли пользователей

### 1. Super Admin

Полные права.
Может:

* создавать и удалять пользователей;
* менять весь контент сайта;
* управлять отзывами;
* управлять карточками кухонь;
* управлять блогом;
* управлять локальными страницами;
* менять цены;
* менять контакты;
* публиковать и снимать с публикации материалы;
* смотреть журнал действий;
* выдавать гостевой доступ.

### 2. Manager / Content Admin

Ограниченный постоянный доступ.
Может:

* редактировать карточки кухонь;
* добавлять и редактировать кейсы;
* менять фото;
* редактировать цены;
* модерировать отзывы;
* редактировать FAQ;
* редактировать блог;
* редактировать часть текстов.

Не может:

* создавать Super Admin;
* менять системные настройки;
* удалять журнал действий;
* менять глобальные настройки безопасности.

### 3. Guest Admin

Временный доступ по одноразовой ссылке, одноразовому логину/паролю или magic link.

Назначение:

* дать временный доступ подрядчику, менеджеру, контент-редактору или партнеру для разового изменения контента.

Guest Admin может только в рамках выданного разрешения:

* добавить новую кухню;
* изменить существующую карточку кухни;
* удалить карточку кухни, если право выдано;
* изменить фото;
* изменить цену;
* изменить описание;
* добавить материалы в галерею;
* сохранить изменения.

Guest Admin не должен иметь доступ:

* к пользователям;
* к системным настройкам;
* к аналитике;
* к журналу действий полностью;
* к SEO-глобальным настройкам;
* к юридическим страницам;
* к отзывам, если это не выдано отдельно.

## 21.4 Требования к гостевому доступу

Гостевой доступ должен поддерживать один из двух безопасных сценариев:

### Сценарий A. Одноразовая ссылка

Super Admin создает временную ссылку с параметрами:

* к какому разделу есть доступ;
* какие действия разрешены: просмотр / создание / редактирование / удаление;
* срок действия ссылки;
* одноразовое или многоразовое использование в рамках времени.

### Сценарий B. Одноразовый логин / пароль

Super Admin создает временные учетные данные, которые:

* действуют ограниченное время;
* после первого входа требуют смену пароля либо автоматически становятся недействительными после завершения сессии;
* имеют жестко ограниченные права.

Для MVP предпочтителен Сценарий A — magic link / одноразовая ссылка.

Обязательные ограничения:

* истечение доступа по времени;
* логирование всех действий;
* возможность немедленно отозвать доступ;
* ограничение по разделам;
* невозможность повысить свои права;
* невозможность массового удаления контента без подтверждения.

Админ-панель должна быть удобной и быстрой.

Требования:

* десктопная версия как основная;
* таблицы со списками материалов;
* быстрые кнопки «Редактировать», «Удалить», «Скрыть», «Опубликовать»;
* drag-and-drop для изображений, если возможно;
* предпросмотр карточки до публикации;
* подтверждение перед удалением;
* автосохранение черновика опционально;
* показ ошибок валидации.

Админ должен иметь возможность:

* загружать новые фото;
* удалять фото;
* заменять фото;
* менять порядок фото в галерее;
* задавать alt-текст;
* задавать подпись;
* выбирать главное фото карточки.

Технические требования:

* поддержка webp/jpg/png;
* ограничение размера файла;
* защита от загрузки недопустимых форматов.

## 21.8 Модерация отзывов

Нужно реализовать правила модерации:

* новые отзывы попадают в статус «На модерации»;
* администратор может «Опубликовать»;
* администратор может «Отклонить»;
* администратор может «Удалить»;
* должна быть возможность указать причину отклонения для внутреннего использования.

Важно:

* на публичной части сайта не должны появляться отзывы без одобрения;
* удаление и отклонение должны логироваться.

## 21.9 Безопасность

Обязательно:

* защита маршрутов /admin;
* secure session handling;
* rate limiting на вход;
* защита от brute-force;
* CSRF/XSS базовая защита;
* серверная валидация форм;
* логирование действий;
* резервный способ доступа для владельца;
* возможность быстро отключить гостевой доступ.

## 21.10 SEO и админ-панель

Через админ-панель должно быть возможно редактировать:

* Title;
* Meta Description;
* H1;
* SEO slug;
* alt-тексты изображений;
* FAQ;
* breadcrumbs label при необходимости;
* canonical только для Super Admin или разработчика.

Нельзя позволять Guest Admin массово менять SEO-параметры всех страниц.

## 21.11 Требования к данным

Все изменяемые сущности должны храниться централизованно:

* кухни;
* кейсы;
* отзывы;
* цены;
* статьи;
* страницы;
* контакты;
* настройки;
* пользователи;
* временные доступы.

Нельзя строить проект так, чтобы для изменения цены или фото нужно было вручную править код.

## 21.12 Критерии приемки для админ-панели

Админ-панель считается готовой, если:

* Super Admin может войти и управлять всем сайтом;
* Manager может редактировать контент без доступа к критическим настройкам;
* Guest Admin может войти по временному доступу;
* Guest Admin может изменить только разрешенные ему разделы;
* можно добавлять, изменять и удалять кухни;
* можно менять фото и цены;
* можно модерировать отзывы;
* все действия логируются;
* удаление требует подтверждения;
* доступ можно отозвать;
* изменения появляются на сайте корректно.

* нельзя скрывать важные коммерческие данные;
* нельзя делать только красивый дизайн без SEO-базы;
* нельзя перегружать первый экран;
* нельзя использовать только стоковые фото, если есть возможность показать реальные;
* нельзя строить сайт полностью вокруг абстрактных “акций” и “скидок”.
* нельзя строить админ-панель так, чтобы любой временный пользователь имел доступ ко всем данным сайта.
* нельзя оставлять временные доступы бессрочными.
* нельзя публиковать отзывы без модерации.

## 32.5 Жесткие правила для ИИ

В файле AI_RULES.md должны быть зафиксированы следующие правила.

### ИИ обязан

* сначала читать документацию, затем писать код;
* не менять архитектуру без записи в CHANGELOG;
* не удалять SEO-структуру без явного основания;
* не ломать маршруты и slug;
* не заменять SSR/SSG на client-only SPA;
* не удалять schema markup;
* не удалять аналитику;
* не менять логику ролей админ-панели без обновления ADMIN_PANEL_SPEC;
* не вносить скрытые зависимости без описания;
* писать переиспользуемые компоненты;
* соблюдать mobile-first подход;
* учитывать Google и Яндекс SEO-ограничения;
* сохранять совместимость с GitHub deployment flow;
* документировать изменения.

### ИИ запрещено

* придумывать новые страницы без логики структуры;
* копировать один и тот же текст на разные городские страницы;
* использовать фейковые отзывы;
* публиковать неутвержденный контент;
* менять URL без причины;
* делать “красиво”, но в ущерб скорости;
* добавлять тяжелые библиотеки без необходимости;
* хранить контент, который должен редактироваться в админке, жестко в коде;
* давать гостевому доступу полные права.

2. Какие файлы будут затронуты
3. Какие риски есть
4. Что будет сделано

# 33. Фичи для отличия от конкурентов

Фичи должны не просто украшать сайт, а усиливать SEO, конверсию, доверие и полезность. В отрасли усиливается спрос на персонализацию, умные решения хранения и технологическую интеграцию, поэтому выигрышнее делать упор на интерактив, прозрачность и практичность, а не только на галерею красивых кухонь. ([houzz.com](https://www.houzz.com/magazine/34-home-design-trends-that-will-define-2025-stsetivw-vs~179446190?utm_source=chatgpt.com))

## 33.1 Фичи для MVP

### 1. Умный калькулятор кухни

Не просто форма, а пошаговый конфигуратор:

* размер кухни;
* форма;
* стиль;
* материал фасада;
* тип столешницы;
* уровень фурнитуры;
* наличие техники;
* бюджет.

Результат:

* ориентировочный диапазон стоимости;
* рекомендации по комплектации;
* захват лида.

Почему это важно:

* помогает пользователю понять бюджет;
* повышает конверсию;
* делает сайт полезнее, чем обычный каталог.

### 2. Подбор кухни по бюджету

Отдельный интерфейс:

* до X;
* X–Y;
* Y–Z;
* премиум.

Показывает релевантные решения, материалы и примеры.

### 3. Подбор кухни по планировке

Пользователь выбирает:

* маленькая кухня;
* кухня-гостиная;
* узкая кухня;
* кухня в новостройке;
* кухня в частном доме.

Далее получает примеры, советы и кейсы.

### 4. Сравнение материалов

Интерактивный блок:

* MDF vs пластик vs эмаль vs шпон;
* цена;
* износостойкость;
* внешний вид;
* уход;
* срок службы.

### 5. Кейсы с реальными цифрами

Для каждой кухни:

* площадь;
* материалы;
* стоимость;
* сроки;
* задачи клиента;
* что было сделано.

### 6. Квиз “получить 3 варианта кухни под ваш бюджет”

Это сильнее стандартной кнопки “оставьте заявку”.

### 7. Фильтр “Смотреть кухни, похожие на вашу задачу”

По:

* бюджету;
* стилю;
* форме;
* цвету;
* площади.

### 8. Блок “Что входит в цену, а что нет”

Снижает недоверие и помогает отстроиться за счет прозрачности.

# 34. Автономный сценарий для Replit: создать файлы, опереться на них и пушить в GitHub

## 34.1 Цель

Если владелец проекта не загружает документацию вручную в GitHub, то ИИ в Replit должен:

* сам создать все проектные файлы документации внутри репозитория;
* сам создать базовую структуру проекта;
* сам использовать эти файлы как источник истины;
* коммитить изменения по этапам;
* пушить изменения в подключенный GitHub-репозиторий.

Важно:

* этот сценарий работает только если Replit-проект действительно подключен к GitHub-репозиторию с правами на push;
* если GitHub в Replit не подключен, ИИ должен сначала создать файлы локально в проекте и подготовить проект к последующему push.

## 34.2 Обязательное поведение Replit AI в самом начале

Прежде чем писать основной код сайта, Replit AI должен выполнить шаги строго в следующем порядке:

### Шаг 1. Проверка Git/GitHub состояния

Проверить:

* инициализирован ли git в проекте;
* есть ли remote origin;
* подключен ли GitHub-репозиторий;
* есть ли права на commit/push.

Если git не инициализирован:

* инициализировать git.

Если нет remote:

* сообщить, что remote не настроен, но продолжить локально.

Если remote есть и push доступен:

* использовать поэтапные коммиты и push.

### Шаг 2. Создание папки проектной документации

Создать папку:

* /project-docs

### Шаг 3. Создание обязательных файлов документации

Создать следующие файлы и заполнить их содержимым на основе этого ТЗ:

* /project-docs/TECHNICAL_SPEC.md
* /project-docs/AI_RULES.md
* /project-docs/CONTENT_RULES.md

## 34.5 Как Replit AI должен вести документацию по ходу проекта

После каждого этапа разработки Replit AI обязан:

* обновить CHANGELOG.md;
* обновить HANDOFF.md;
* обновить COMPONENT_LIBRARY.md если добавились компоненты;
* обновить ROUTES_MAP.md если добавились маршруты;
* обновить ADMIN_PANEL_SPEC.md если изменилась логика ролей;

## 34.6 Правило источника истины

Для Replit AI источником истины являются:

1. файлы из /project-docs;
2. текущая структура проекта;
3. уже принятые решения в CHANGELOG.md и HANDOFF.md.

Replit AI не должен:

* игнорировать проектную документацию;
* заменять её своими догадками;
* silently менять архитектуру;
* удалять документацию как “лишнюю”.

## 34.9 Что нельзя поручать Replit делать “по памяти”

Нельзя просить Replit:

* “сделай сайт как-нибудь сам”;

* “потом добавим SEO”;

Сначала документация, потом архитектура, потом код.
